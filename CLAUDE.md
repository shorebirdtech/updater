## What This Is

Shorebird's updater library — a Rust core that gets linked into Flutter Engine (`libflutter.so`) as a static C library to enable over-the-air code push for Flutter apps. The Dart package (`shorebird_code_push`) calls into it via FFI.

## Build & Test

```bash
# Rust (from workspace root or individual crate dir)
cargo build --verbose
cargo test
cargo llvm-cov --lcov --output-path lcov.info   # tests + coverage (CI uses this)
# Prerequisites for coverage: rustup component add llvm-tools-preview && cargo install cargo-llvm-cov

# Dart package
cd shorebird_code_push
flutter pub get
flutter test --coverage
dart format --set-exit-if-changed .
dart analyze --fatal-warnings lib test
```

Rust tests that call `shorebird_init` must run single-threaded — use the `#[serial]` attribute from `serial_test`. The global static config means concurrent `shorebird_init` calls stomp each other, so any test that touches init needs `#[serial]`.

## Workspace Layout

Cargo workspace with two members: `library` (core updater) and `patch` (CLI tool for packaging patches). The Dart FFI package lives in `shorebird_code_push/`.

## Architecture (library/)

Layers from outside in:

1. **C API** (`c_api/mod.rs`) — stable C interface consumed by Flutter Engine; thin wrapper around Rust API. `c_file.rs` provides a read-seek interface for iOS patch files.
2. **Rust API** (`updater.rs`, re-exported from `lib.rs`) — core logic including the boot state machine and patch check/update state machines.
3. **Cache** (`cache/`) — on-disk state via `patches_state.json`. `updater_state.rs` is the public API; `patch_manager.rs` manages patch files; `signing.rs` handles cryptographic verification.
4. **Network** (`network.rs`) — server communication for patch checks and downloads.
5. **Platform** (`android.rs`, `logging.rs`) — platform-specific integration (Android logcat, iOS oslog, etc.).

Thread safety: global config object with locking, since it's called from both `flutter_main` thread (init) and Dart/UI thread (updates).

Design principle: "fail open" — always fall back to the currently installed version; never leave the app in a broken state.

## Key Details

- C headers (`include/updater_dart.h` for the ffigen-consumed Dart-stable surface, `include/updater_engine.h` for the engine-internal surface) are auto-generated by `cbindgen` via `build.rs` — don't edit manually. The two configs live at `library/cbindgen_dart.toml` and `library/cbindgen_engine.toml`.
- Dart FFI bindings (`updater_bindings.g.dart`) are generated by `ffigen` — don't edit manually.
- Library builds as three crate types: `lib` (Rust tests), `cdylib` (Dart FFI testing), `staticlib` (engine linking).
- Boot state machine docs: `docs/boot_state_machine.md`.
- `fixtures/` is a language-neutral corpus of updater behavior (on-disk state, patch checks, boot/crash sequences, bipatch goldens) replayed through the C API by `library_test_hooks/tests/fixture_corpus.rs`. A behavior change shows up there; format in `fixtures/README.md`.
- CI requires semantic PR titles (conventional commits style).
- Issues for this repo (the Rust updater, the C API and `shorebird_code_push`) live in `shorebirdtech/shorebird`, labels `updater` and `package_code_push`; this repo has issues disabled. Search and file there. PRs still come here.

## FFI compatibility

The Dart `shorebird_code_push` package and the Rust library ship independently: the Rust side is built into the Shorebird engine, while the Dart package is a pub dependency the app picks its own version of. Both skews happen (new Dart on an old engine, old Dart on a new engine). Beyond the package's Flutter SDK floor in `shorebird_code_push/pubspec.yaml`, which only bounds the oldest engine, nothing pins or negotiates versions between them. So every change to the Dart-stable surface (`library/src/c_api/dart.rs`, which generates `include/updater_dart.h`) must state its fallback for both skews. The engine surface (`c_api/engine.rs`, `include/updater_engine.h`) ships with the engine and isn't bound by these rules.

- New C symbols may be missing on an older engine. The ffigen bindings (`UpdaterBindings(DynamicLibrary.process())`) throw on first use of a missing symbol, so Dart must probe a new symbol before calling it (`DynamicLibrary.providesSymbol`, or a guarded lookup) and fall back when it's absent.
- Existing structs, including `UpdateResult`, have a frozen layout. New data goes in a new struct returned by a new symbol, not in new fields.
- Status codes are append-only and never renumbered. A new *error* code degrades safely (old Dart maps it to `unknown`). A new *success or benign* code doesn't: old Dart checks success against a fixed allowlist and reports the new code as a failure. `SHOREBIRD_UPDATE_IN_PROGRESS` (4) already does this on packages older than #335. Don't add more.
- Failure categories stay below the boundary until a structured-result symbol exposes them; see the doc comments on `FailureCategory` (`library/src/updater.rs`) and `NetworkError` (`library/src/network.rs`).

## Landing a PR

No review bot runs here, so a PR lands with `--admin` once these hold at its head commit:

- a separate agent's adversarial review of the full diff is posted as a PR comment, and its blockers are fixed or answered;
- a maintainer has LGTM'd (a `lgtm` comment, an approval, or they opened the PR). Agents never post `lgtm` or approve. Rebases and small fixes keep an LGTM; a change of scope needs a new one;
- `gh pr checks <N> --required` is all green, nothing pending, and no review thread is open. `--admin` skips GitHub's gates, so check right before merging.

```sh
gh pr merge <N> --admin --squash --match-head-commit <full sha>
```
